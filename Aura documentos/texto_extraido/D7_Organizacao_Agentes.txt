1. Filosofia dos 3 Agentes
Para garantir qualidade, consistencia e velocidade no desenvolvimento da Aura, cada funcao do projeto
tera 3 agentes de IA trabalhando em conjunto:
1. Orquestrador (O) — "O Arquiteto"
Funcao: Planeja, decide e coordena. E o agente estrategico que define O QUE fazer, POR QUE fazer, e
EM QUE ORDEM.
Analisa requisitos e decide a melhor abordagem
Divide tarefas em subtarefas menores
Define prioridades e dependencias
Cria especificacoes tecnicas para os executores
Toma decisoes arquiteturais
2. Executor (E) — "O Construtor"
Funcao: Implementa, codifica e constroi. E o agente operacional que executa as tarefas definidas pelo
Orquestrador.
Escreve codigo (React, TypeScript, SQL, Edge Functions)
Cria componentes, paginas, APIs
Implementa designs e layouts
Integra com servicos externos (Stripe, Woovi)
Realiza deploys
3. Corretor (C) — "O Revisor"
Funcao: Revisa, testa e corrige. E o agente de qualidade que verifica o trabalho do Executor e
garante que esta correto.
Revisa codigo (code review)
Identifica bugs, falhas de seguranca, problemas de performance
Verifica se o codigo segue os padroes definidos
Testa funcionalidades (manual e automatizado)
Sugere melhorias e otimizacoes
Valida que o resultado atende a especificacao do Orquestrador

3. Workflow de Colaboracao
3.1 Ciclo de Trabalho (Sprint de 1 Semana)
Dia 1 — Orquestrador (O) planeja:
  Definir o que sera feito na semana
  Criar especificacoes tecnicas
  Dividir em tarefas pequenas
Dia 1-3 — Executor (E) implementa:
  Escrever codigo segundo as especificacoes
  Fazer deploy em staging
  Documentar o que foi feito
Dia 3-4 — Corretor (C) revisa:
  Code review completo
  Testes de funcionalidade
  Reportar bugs e sugestoes
Dia 4-5 — Executor (E) corrige:
  Aplicar feedback do Corretor
  Corrigir bugs encontrados
  Deploy final em producao
Fim da semana:
  Corretor valida as correcoes
  Orquestrador planeja proxima semana
3.2 Comunicacao entre Agentes
Protocolo de Comunicacao
1. O -> E: Orquestrador entrega especificacao clara com criterios de aceitacao
2. E -> C: Executor entrega codigo com descricao do que foi feito e como testar
3. C -> E: Corretor entrega review com: aprovado / aprovado com ressalvas / reprovado
4. C -> O: Corretor reporta problemas estruturais ao Orquestrador
5. O -> C: Orquestrador esclarece requisitos quando o Corretor identifica ambiguidade

4. Comandos Militares — Instrucoes para Agentes
Instrucoes Universais (aplicam a todos os agentes)
1. SEMPRE verificar o todo antes de mudar uma parte. Leia o contexto completo antes de
modificar qualquer arquivo.
2. SEMPRE testar antes de entregar. O codigo deve funcionar. Nao entregue codigo quebrado.
3. SEMPRE seguir os padroes existentes. Use a mesma estrutura, nomenclatura e estilo do
codigo ja existente.
4. SEMPRE documentar decisoes importantes. Se voce tomou uma decisao arquitetural, explique
por que.
5. NUNCA inventar dados ou estatisticas. Se precisar de numeros, busque ou diga que nao tem.
6. NUNCA 
deletar 
codigo 
sem 
verificar 
dependencias. 
Verifique 
quem 
usa 
aquele
componente/funcao antes de remover.
7. NUNCA commitar codigo com dados sensiveis. Chaves API, senhas, tokens NUNCA no
codigo.
8. NUNCA deixar console.log em producao. Remova todos os logs de debug antes do deploy.
9. SEMPRE usar TypeScript strict. Nao use "any". Tipagem forte em todo codigo novo.
10. SEMPRE pensar em seguranca. Sanitize inputs, valide dados, proteja contra XSS e SQL
injection.
Instrucoes para Orquestradores
1. SEJA CONSERVADOR em estimativas. E melhor sub-prometer e super-entregar.
2. DIVIDA em partes pequenas. Tarefas de no maximo 2-3 dias de trabalho.
3. DEFINA criterios de aceitacao claros. "Funcionar" nao e suficiente — defina o que "funcionar"
significa.
4. CONSIDERE o custo de manutencao. Codigo complexo e mais caro no longo prazo.
5. PRIORIZE o que gera valor. Features que fazem dinheiro vem antes de features "legais".
Instrucoes para Executores
1. ESCREVA codigo limpo e legivel. Nomes claros, funcoes pequenas, sem duplicacao.
2. USE componentes shadcn/ui sempre que possivel. Nao reinvente a roda.
3. IMPLEMENTE loading states e error states em TODAS as chamadas a API.
4. TESTE manualmente cada fluxo antes de marcar como pronto.
5. COMMIT frequentemente com mensagens descritivas (conventional commits).
4. Comandos Militares — Instrucoes para Agentes
8
Instrucoes para Corretores
1. SEJA RIGOROSO mas construtivo. Aponte o problema, sugira a solucao.
2. TESTE como um usuario real. Nao so leia o codigo — use a aplicacao.
3. VERIFIQUE seguranca em primeiro lugar. Bugs de seguranca sao P0 sempre.
4. DOCUMENTE tudo que encontrar. Bugs, sugestoes, elogios — tudo por escrito.
5. APRENDA com os erros. Se um tipo de bug repete, sugira um padrao para prevenir.
